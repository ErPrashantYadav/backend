## 2. Global Architecture & Authentication Rules

### 2.1 Public Storefront Access (Guest Model)

- **Zero Registration Barrier**: Customers checkout as guests without passwords or persistent user accounts.
- **Cart Tracking**: Ephemeral cart sessions use `X-Cart-Id` request/response headers or query parameters.
- **Order Lookup Security**: Looking up an order or submitting payment proofs requires an opaque, 64-character unguessable lookup token via `X-Order-Lookup-Token` header, `X-Order-Token` header, or `orderLookupToken` body field. Raw database orders never expose hash values.
- **Checkout Eligibility**: Checkout enforces an **NPR 800 minimum eligible subtotal** after item-level catalog discounts and before promo code deductions.
- **GPS Coordinates**: Kathmandu delivery calculations evaluate customer coordinates against store origin (`STORE_ORIGIN_LATITUDE`, `STORE_ORIGIN_LONGITUDE`) to compute road distance and per-km delivery fees.

### 2.2 RBAC Administrative Access

- **Authentication**: `Authorization: Bearer <JWT_ACCESS_TOKEN>` header.
- **Token Properties**: Lifetime is fixed at 900 seconds (15 minutes); verified with `JWT_SECRET`, `JWT_ISSUER`, and `JWT_AUDIENCE`.
- **Dynamic Permission Check**: Every authenticated request re-evaluates admin account status (`isActive: true`), role status (`isActive: true`), and active permissions from database records.
- **Superadmin Bypass**: The `admin.system.manage` permission grants wildcard access across all administrative operations.

## 4. Route Aliases & Convenience Mounts

To guarantee maximum frontend compatibility across mobile applications, web storefronts, and internal administrative tooling, the Liquor Shop backend exposes several well-defined convenience route aliases. These aliases execute identical controller actions and security middleware as their canonical counterparts:

| Canonical Endpoint                                                              | Implemented Alias(es)                                                                                   | Rationale & Use Case                                                                                                            |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/settings`<br>`PATCH /api/admin/settings`                              | `GET /api/store-settings`<br>`PATCH /api/admin/store-settings`                                          | Allows frontend clients to use either concise `/settings` or descriptive `/store-settings`.                                     |
| `POST /api/contact`<br>`GET /api/admin/contact-inquiries`                       | `POST /api/contact-inquiries`<br>`GET /api/admin/contact`                                               | Allows singular (`/contact`) or plural (`/contact-inquiries`) REST convention.                                                  |

## 5. Explicitly Blocked Reordering Endpoints (Negative Security Contract)

A strict design principle of the Liquor Shop architecture is that persistent manual drag-and-drop reordering is **only supported for Brands and Banners**. All other catalog and showcase entities deliberately omit reorder routes and return `404 Not Found`:

1. `PUT /api/admin/categories/reorder` ➔ **404 Not Found**
2. `PUT /api/admin/products/reorder` ➔ **404 Not Found**
3. `PUT /api/admin/gallery/reorder` ➔ **404 Not Found**
4. `PUT /api/admin/social-media/reorder` ➔ **404 Not Found**

Both the OpenAPI specification and Postman collection folder `18. Negative Cases & Forbidden Reorder Endpoints` explicitly test and assert this contract.
